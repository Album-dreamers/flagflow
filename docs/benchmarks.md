# 压测与故障验证

测试条件：

- 阿里云 4 vCPU / 7 GB，压测端、服务端、PostgreSQL 在**同一台机器**上；
- 服务端是单个 uvicorn 进程（uvloop），Python 3.11；
- 项目有 20 个开关；
- 延迟从版本提交那一刻算到客户端收到为止，包含压测端解析流的开销。

脚本和用法见 [`server/loadtest/`](../server/loadtest/README.md)。下面每个数字的原始数据、机器配置和运行命令都在 [`server/loadtest/results/`](../server/loadtest/results/README.md)，可以用 `report.py` 重新算出来。

**单实例推送扩散**（客户端只保持 SSE 连接）

| SSE 连接数 | 送达 | 提交 → 收到事件 P50 / P99 | 服务进程内存 |
|---|---|---|---|
| 1,000 | 100% | 135 / 484 ms | 156 MB |
| 2,000 | 100% | 323 / 843 ms | 214 MB |
| 5,000 | 100% | 1.42 / 1.94 s | 380 MB |
| 10,000（修复前） | 37.9%，只有 4,416 个客户端收到过推送 | — | 535 MB |
| 10,000（修复后） | **100%**（10 万次投递） | 3.03 / 4.16 s | 656 MB |

**收到推送后回拉配置**（1,000 个客户端，每 10 秒发布一次）

| | 缓存前 | 缓存后 |
|---|---|---|
| 追上最新版本的客户端 | 0 / 1,000 | **1,000 / 1,000** |
| 提交 → 配置生效 P99 | 35.2 s | **5.10 s** |
| 提交 → 收到事件 P99 | 19.3 s | **0.73 s** |

"生效"的判定：`/sync` 返回 200、版本号不低于事件里的版本号、20 个开关齐全，三项都满足才算。不满足的记为失败，客户端停在旧版本，等下一次事件再拉。连接层面的错误（比如连接被服务端关掉）同样记为失败；早先的脚本会漏记这类错误，相关几组已用修正后的脚本重跑。两组测试的 `/sync` 都是零失败。"缓存后"这一列是加上这项校验之后重跑的结果。

**大量客户端同时启动**（1,000 个客户端以每秒 50 个的速度启动，每个都先调一次 `/flags/load`，之后照常回拉）

| | 修复前 | 修复后 |
|---|---|---|
| `/flags/load` 失败率 | 89.2% | **0%** |
| 追上最新版本的客户端 | 152 / 1,000 | **1,000 / 1,000** |
| `/flags/load` 平均耗时 | 11.6 s | **0.45 s** |

两组都使用默认的连接池大小（10）。修复前，把连接池调到 40 只能把失败率降到 47.5%，单次加载反而更慢（平均 21.9 s）；修复后，连接池 10 和 40 下 `/flags/load` 都是零失败。连接池 40 那轮有 40 次（0.8%）`/sync` 撞上服务端关闭空闲的 keep-alive 连接（uvicorn 默认 5 秒）：压测客户端用的 requests 不淘汰空闲连接，两次发布间隔 10 秒；这些客户端在下一次事件补拉成功，最终 1,000 个全部追上。SDK 用的 httpx 默认 5 秒就淘汰空闲连接。

**故障测试**

- PostgreSQL 重启：数据库刚恢复、Hub 还没重连上时提交一个版本，它的 NOTIFY 无人接收，但仍然靠重连后的补对送达了全部 300 个客户端（P50 0.95 s）。全程 2,100 次投递全部送达，回拉零失败。
- 两个 http 实例各连 500 个客户端，只写入一次：5,000 次投递全部送达，P99 0.80 s。
- 服务重启：SDK 带 jitter 重连，重连成功时立即拿到停机期间提交的版本。

## 结果如何解读

事件送达与配置回拉是两种不同的指标：万连接测试只保持 SSE 流，没有为每个客户端执行 `/sync`。1,000 客户端回拉测试才包含配置请求，不能把两组数字合并成“万客户端配置在相同时间内生效”。

这些数据来自归档中的特定提交与测试条件，不是当前所有功能、部署方式的性能承诺。发布间隔短于回拉耗时时，慢客户端会直接拿到最新版本、跳过中间版本；`report.py` 把跳过的版本计为未送达，所以要看"追上最终版本的客户端"，而不是逐版本的送达率。
